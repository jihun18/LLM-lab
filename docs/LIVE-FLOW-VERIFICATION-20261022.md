# 실제 화면·API·USB 모델 연결 검증 — 2026-10-22

## 검증한 사용자 흐름

브라우저에서 질문/문서 추가 → FastAPI API → Wiki 또는 USB의 Ollama 모델 → NDJSON → 부분 답변/일반 답변/출처 화면을 확인했다. 이전 격리 목업 테스트와 달리 이번에는 사용자가 실행한 실제 `http://127.0.0.1:8000` 서버와 `127.0.0.1:11434` Ollama를 사용했다. 서버를 직접 시작·재시작하거나 코드를 고치지 않았다.

초기에는 8000 연결 거부로 전체 흐름 검증의 첫 경계에서 멈췄다. 사용자가 서버를 실행한 뒤에 아래 검증을 이어갔다.

## 기준 상태

- `/` HTTP 200, 제공된 HTML은 디스크의 새 `privAI.html`과 바이트 일치
- `/health` HTTP 200, FastAPI, Ollama 연결 정상
- `/models` HTTP 200, 설치된 생성 3개 및 임베딩 2개 목록 확인
- `/knowledge/status` HTTP 200, BM25, 문서 18개·조각 74개
- Ollama `/api/show`에서 qwen3:1.7b의 실제 FROM이 `D:\OllamaModels\blobs\sha256-3d0b790534fe4b79525fc3692950408dca41171676ed7e21db57af5c65ef6ab6`임을 확인

Chrome을 headless로 실행했지만 응답을 가로채거나 목업하지 않고 실제 화면 폼을 조작했다. 각 API 응답·본문·화면을 기록했고 pageerror는 0개다. 사용자 PowerShell의 서버 stdout은 직접 읽지 않았으므로 서버 내부 경고가 전혀 없었다고 주장하지 않는다.

업로드는 개인정보 없는 250바이트 TXT이며 실제 지원정책이 아닌 화면 검증용 가상 문서임을 본문에 명시했다. 생성된 경로는 `Uploads/ui-flow-check-20261022-1792633438999-cf8a492964.md`다. 업로드 후 실제 파일 생성·자동 색인·검색 출처·화면을 연결해 확인했다.

## 테스트 데이터 정리

검증 뒤 이 테스트 파일 하나만 `benchmark-results/answer-ui-live-20261022/uploaded-test-document.md`로 이동해 복구 가능한 상태로 보존했다. 기존 사용자 업로드는 건드리지 않았다. `/knowledge/reindex` 200으로 문서 18개·조각 74개를 복원했고 `/documents`에서 테스트 파일이 활성 목록에 없는 것도 확인했다. UI 화면 캡처는 정리 전 검증 순간의 19개 문서 상태를 보여준다. 기존 열린 브라우저는 새로고침하면 복원된 색인 상태를 읽는다.

## 재현 근거와 범위

로컬 검증 폴더는 `benchmark-results/answer-ui-live-20261022/`다. 실제 브라우저 검증 스크립트 `verify.cjs`, API/NDJSON 기록 `report.json`, `partial.png`, `generated.png`, `upload-answer.png` 및 보관한 테스트 문서가 들어 있다. 화면 3개를 직접 확인했다. 이 로컬 산출물은 Git에 포함하지 않는다.

이번 범위의 필수 UI/API 요청은 전부 200이며 실제 입력부터 결과 표시까지 연결됐다. 수정이 필요한 기능 오류는 발견하지 않았다. 진단·기록만 했고 운영 코드·모델·설정은 변경하지 않았다. 이전 pytest 450개와 화면 로직 11개 결과는 별도 회귀 검증이며 이번 실제 흐름 검증에서 다시 전체 실행한 것은 아니다. 모든 질문·PDF 업로드·다른 모델·모든 브라우저의 정확성을 보장하는 검증은 아니다.
