# 메모리 수집 지연 진단 — 2026-10-08

## 결론

관찰된 큰 공백의 주요 구간은 **스냅샷 호출 내부의 경과 시간**이다. 단순히 목표 시각까지의 대기만 길어지는 문제가 아니다. 다만 이 시간에는 프로세스 조회와 실행 스케줄링 지연이 함께 들어가므로 psutil의 CPU 계산 비용이나 특정 함수가 원인이라고 아직 확정하지 않는다. 운영 수집 방식·안전 검사·모델 상태는 변경하지 않았다.

대상은 같은 `absolute-deadline-v2` 방식의 [1.7B 재측정](MEMORY-MEASUREMENT-20261008.md)·[4B](MEMORY-MEASUREMENT-4B-20261008.md)·[7B](MEMORY-MEASUREMENT-7B-20261008.md) 원자료다. 원자료 파일명·지문은 각 문서에 보존했다. 새 모델 생성 없이 기존 기록만 읽었다.

## 분리 방법

연속 표본의 시간차를 아래처럼 분리하고 모든 요청 구간에서 합계가 일치함을 확인했다.

`다음 시작 - 현재 시작 = (현재 read_end - 현재 시작) + (다음 시작 - 현재 read_end)`

- 앞 항은 스냅샷 내부 경과 시간이다. `members()` 범위 검사, RSS 읽기, PID 재확인 및 호출 중 실행 대기를 포함한다.
- 뒤 항은 스냅샷 종료 이후 다음 시작까지 시간이다. 의도한 대기·목표 시각 건너뛰기·스케줄러 작업·종료 경계 처리 등이 섞인다. 전체를 불필요한 지연이나 OS 대기라고 부르지 않는다.
- 주기 표본의 `time - schedule.target_time`은 목표 시각 대비 시작 지연이다. 실제 `Event.wait` 호출/반환 시각은 없어 순수 wakeup 비용으로 분리할 수 없다.

읽기 시간 통계는 요청 5회의 시작/주기/끝 표본을 모두 포함한다. 목표 시각 지연 통계는 주기 표본만 사용한다. 유휴는 별도다. p95는 정렬 후 `ceil(0.95 × 표본 수)` 위치의 값(nearest-rank)이다.

## 스냅샷 내부 경과 시간

단위 ms. 같은 환경을 완전히 통제한 인과 실험은 아니므로 모델 크기만의 영향이라고 주장하지 않는다.

| 모델 | 표본 수 | 읽기 평균 | 읽기 p95 | 읽기 최대 | 100ms 초과 읽기 수 | 유휴 읽기 평균 |
|---|---:|---:|---:|---:|---:|---:|
| qwen3:1.7b | 166 | 44.94 | 66.77 | 151.76 | 4 | 50.67 |
| qwen3:4b-instruct | 321 | 57.59 | 113.98 | 316.72 | 20 | 41.74 |
| qwen2.5:7b-instruct | 487 | 94.12 | 283.80 | 937.50 | 86 | 45.23 |

7B에서는 요청 중 평균 읽기 시간이 94.12ms로 100ms 목표 간격 대부분에 해당한다. 유휴 평균 45.23ms보다 길었지만 CPU/GIL/OS 상태별 기록이 없어 원인은 아직 분리되지 않았다. 함수 경과 시간을 CPU 사용률로 해석하지 않는다.

## 가장 긴 7B 공백

3회차의 0부터 센 표본 인덱스 6→7:

- 현재 시작: 7445.2831341, 읽기 종료: 7446.220637
- 다음 시작: 7446.3554594
- 전체 간격: 1,072.33ms = 내부 읽기 937.50ms + 읽기 종료 후 134.82ms
- 내부 경과 시간은 해당 공백의 87.43%다. 다음 표본의 목표 시각 대비 지연은 97.37ms이며 위 134.82ms에 이미 포함되는 요소이므로 별도로 더하지 않는다.
- 다음 주기 tick은 8에서 18로 이동해 중간 목표 9개를 건너뛰었다. 누락은 원자료에 그대로 남아 있다.

실제 시각은 perf_counter 기준 로컬 단조 시각이며 날짜/시각으로 해석하지 않는다. 관측 최대 RSS는 이 공백 동안의 실제 피크를 복원하지 못한다.

## 코드에서 확인한 비용 후보

`core/memory_sampling.py`의 `members()`는 매 스냅샷마다 웹 서버·runner·서비스의 `children(recursive=True)`를 각각 호출하고, 콘솔 호스트 부모·실행 경로·생성 시각도 검사한다. 이어 `snapshot()`에서 범위별 RSS를 읽고 각 PID의 생성 시각을 다시 확인한다.

설치된 psutil 7.0.0 소스를 읽어 `Process.children()`이 호출마다 `_ppid_map()`을 읽는 것을 확인했다(`.venv/Lib/site-packages/psutil/__init__.py`, children 구현). Windows에서는 해당 함수가 네이티브 `ppid_map`으로 연결된다(`_pswindows.py`). 이것은 반복 조회가 존재한다는 코드 근거이며, 세 번 조회가 937ms의 대부분을 차지했다는 실측 증거는 아니다. 네이티브 함수 내부 비용은 이 분석에서 계측하지 않았다.

## 다음에 필요한 계측

현재 원자료로 확인한 것은 긴 지연의 위치까지다. 원인 확정과 개선 전에는 다음을 별도로 기록해야 한다.

1. 범위 확인 `members()`·RSS 읽기·PID 재확인의 각 단계 시작/종료 경과 시간
2. 동일 구간의 수집기 스레드 CPU 시간과 실제 대기 호출 전후 시각
3. 기존 RSS 경계·검사 빈도·PID 고정·오류 중단 조건을 유지한 재측정

계측 자체의 비용도 비교하고 기존 원자료는 변경하지 않는다. 원인 분리 전에 안전 검사를 줄이거나 캐시로 대체하지 않는다. 7B의 정밀 순간 피크 비교는 계속 보류한다.
