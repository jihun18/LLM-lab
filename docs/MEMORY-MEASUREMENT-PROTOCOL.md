# 웹 서버·Ollama 분리 메모리 측정 기준

상태: **기준 정의 완료, 실제 측정 미실행**. 운영 서버·모델 상태를 변경하지 않았다.

기준 파일: `memory_measurement_protocol.json` (`memory-rss-warm-v1`). 실행 도구가 아직 이 기준을 읽어 측정하도록 구현된 것은 아니다.

## 먼저 확인한 기존 기록의 한계

`benchmark.py`는 `psutil.Process()`로 측정 프로그램 자신의 RSS를 요청 전후에 읽고 `client_memory_delta_mb`를 기록한다. 이 값은 웹 서버나 Ollama의 메모리도 아니고, 요청 중 최대/평균/최소도 아니다. 이름은 그대로 두며 이번 실측과 합치거나 재해석하지 않는다. 기존 속도 실측도 메모리 근거로 바꾸지 않는다.

## 1차 측정 범위

먼저 **FastAPI + qwen3:1.7b** 한 조합으로 수집이 가능한지 확인한다. 이후 같은 기준으로 Flask를 비교한다. 4B·7B, Streamlit, RAG 및 모델 최초 적재 측정은 후속 별도 실험이다.

| 범위 | 포함 | 제외·주의 |
|---|---|---|
| 웹 서버 | 실제 FastAPI 서버 PID와 확인된 자식 프로세스 | 브라우저·측정 클라이언트·Ollama 제외 |
| Ollama 서비스 | 요청을 받는 실제 서비스 프로세스 | 모델 runner를 같은 행에 합치지 않음 |
| Ollama 모델 실행 | 해당 모델을 실행하는 확인된 runner와 자식 | 서비스와 중복 집계하지 않음 |

이름만 보고 모든 python/ollama 프로세스를 더하지 않는다. PID·생성 시각·부모 관계·명령행 및 활성 모델 정보를 대조하여 역할과 범위를 확정한다. 서비스와 runner가 분리되지 않은 환경은 미분리 상태로 기록하고 별도 수치인 것처럼 만들지 않는다. runner를 식별하지 못하면 Ollama 측정은 미확인이다. 접근 거부나 프로세스 종료를 0으로 처리하지 않는다.

샘플마다 구성원을 확인하고 `(PID, 생성 시각)`으로 중복을 제거한다. PID 변경과 runner 교체는 원자료에 남긴다. 범위 누락이 발생한 회차는 비교 집계에서 제외하며 오류와 실제 확보한 원자료를 유지한다.

## 고정 입력과 실행 조건

- 모델: `qwen3:1.7b`. 설치된 정확한 모델 식별자·digest를 실행 직전에 기록한다.
- 질문: `경량 LLM의 장점을 한국어로 두 문장만 설명해줘.`
- 시스템 문구: `간결하고 정확한 한국어로 답하세요.`
- 일반 생성 `/chat`, 비스트리밍, RAG 미사용. 현재 코드의 Qwen3 `/no_think` 덧붙임도 동일하게 적용한다.
- 컨텍스트 2,048, 최대 출력 256, temperature 0.3, think false. 기존 설정의 **기본값**과 맞추되 실제 실행 설정을 먼저 확인한다. 환경 변수로 달라졌으면 일치시키기 전에는 비교 실측을 시작하지 않는다.
- 같은 코드 상태, Python·프레임워크·Ollama 버전, CPU·운영체제, 전원 상태, 모델 적재 상태를 기록한다. 비밀 환경 변수나 전체 환경 덤프는 수집하지 않는다.
- 동시 요청 1개. 다른 모델 생성, 재색인, 문서 업로드, 모델 다운로드, 다른 프레임워크 실험과 섞지 않는다. 기존 사용자 작업을 임의 종료하거나 다른 모델을 자동으로 내리지 않는다. 격리가 안 되면 중단하고 알려준다.

FastAPI/Flask는 Wiki 인덱스 등 현재 앱의 초기화가 포함된 **프로젝트 서버 메모리**다. 프레임워크 라이브러리 자체의 순수 사용량으로 해석하지 않는다. Streamlit은 같은 HTTP `/chat` 비교 경로가 아니므로 현재 화면 요청을 이 결과와 직접 섞지 않는다.

## 시간 구간과 반복

1. 프로세스 식별과 샘플 수집 가능 여부를 먼저 확인한다. 코드나 Wiki를 변경하지 않는다.
2. 같은 모델·입력으로 예열 요청 1회. 정상 답변 및 실제 생성이 있었는지 확인하고 측정 요약에서는 제외한다.
3. 예열 후 요청 없는 5초를 샘플링해 **warm 유휴 기준선**으로 보관한다.
4. 측정 요청 5회를 순차 실행한다. 회차 사이 최소 3초 대기하며 다른 요청이 없는지 확인한다.
5. 각 회차의 주 구간은 요청 직전부터 전체 HTTP 응답 수신 완료까지다. 시작·끝 샘플을 남긴다. 유휴 기준선과 요청 구간을 같은 평균으로 섞지 않는다.

이 실험은 모델 적재 후 요청이다. 최초 적재 비용이나 콜드 스타트를 측정했다는 주장을 하지 않는다. 오류·시간 초과·생성 없음은 무효 회차로 기록하고 성공값에 섞지 않는다. 실패를 숨기는 자동 재시도 대신, 재실행한다면 새 회차 번호와 이유를 남긴다. 5개 유효 회차가 확보되지 않으면 불완전한 실험으로 표시한다.

## 지표와 계산

지표는 `memory_info().rss`이며 원자료는 바이트, 표시 단위는 `MiB = bytes / 1,048,576`이다. Windows의 RSS는 working set에 해당한다. [psutil 공식 문서](https://psutil.readthedocs.io/stable/index.html#psutil.Process.memory_info)

- 계획 샘플 간격: 100ms. 실제 시각과 실제 간격을 함께 기록한다. 수집 지연이 크면 간격 통계와 품질 저하를 표시한다.
- 각 범위의 시각별 값: 그 시각의 확인된 구성원 RSS 합계. 서비스와 runner의 소속 중복은 금지한다.
- 회차별 최소·최대: **해당 요청 구간에서 관측된 표본**의 최소·최대다. 프로세스 시작 이후 peak나 연속 관측의 절대 최고값과 구분한다.
- 회차별 평균: 요청 구간에서 이전 표본 값을 다음 시각까지 유지하는 시간 가중 평균 `sum(RSS_i × dt_i) / 요청 구간 길이`. 수집 간격이 흔들려도 단순 표본 평균으로 바꾸지 않는다. 시작/종료 표본이 없거나 값이 누락되면 유효 평균을 만들지 않는다.
- 유휴 기준선 평균과 요청 평균의 차이는 보조 지표다. 음수 차이는 0으로 잘라내지 않는다. 최대값·평균값·최소값을 서로 대신 쓰지 않는다.
- 프로세스 RSS 합에는 공유 메모리 페이지의 중복 가능성이 있으므로 PC 전체의 고유 물리 메모리 사용량이라고 주장하지 않는다. [psutil 메모리 지표 설명](https://psutil.readthedocs.io/stable/index.html#psutil.Process.memory_full_info)

최종 요약에서도 5회 각각의 행을 유지한다. 회차 최대값의 평균을 ‘최대 메모리’라고 부르지 않고 ‘회차별 표본 최대의 평균’처럼 명시한다. 요청 구간, 유휴 구간, 서비스, runner, 웹 서버를 각각 구분한다.

## 저장할 자료와 Wiki 반영 기준

로컬 `benchmark-results/`에 세 종류를 남긴다.

1. 실행 정보: 프로토콜 ID·해시, 코드 커밋/변경 상태, 실제 옵션·모델 digest, 환경, PID 구성, 샘플 간격, 시작·종료 시각, 오류/무효 사유.
2. 원시 표본: 회차·단조 시각·구간·범위·PID와 생성 시각·바이트 RSS·읽기 실패. 성공하지 않은 값은 null/오류이지 0이 아니다.
3. 회차 요약: 범위별 최소/시간 가중 평균/표본 최대 RSS, 기준선, 응답시간, 출력 토큰 수, 생성속도, 표본 수·유효 여부. 출력 길이가 다를 수 있으므로 같은 질문만으로 같은 작업량이라 단정하지 않는다.

Wiki에는 **실제 수집과 검토를 마친 뒤**만 반영한다. 예시 숫자나 빈 표를 실측처럼 추가하지 않는다. 각 표의 도구 열과 모델·조건 열, `최대 RSS`·`평균 RSS`·`최소 RSS`를 명시한다. 웹 서버, Ollama 서비스, 모델 runner는 별도 표로 두며 조건에는 `warm 요청 중 100ms 표본 / 회차 번호 / 측정 범위`를 포함한다. 여러 회차를 하나로 임의 선택할 수 없도록 질문에서 회차를 지정하거나, 사람이 승인한 요약 정책을 별도로 정한다.

Ollama를 포함한 값을 FastAPI 자체 메모리로 이름 붙이지 않는다. 새 자료가 있다는 이유만으로 자동 우열 판단을 만들지 않는다. 원시 자료는 Git에 자동 추가하지 않으며 Wiki 공개 범위도 검토 후 결정한다.
