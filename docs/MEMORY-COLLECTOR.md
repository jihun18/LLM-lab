# 분리 메모리 수집 도구 — 2026-10-08

## 상태

`memory_benchmark.py`와 `core/memory_sampling.py` 구현 당시 전체 테스트 275개가 통과했다. 사용자 PowerShell 실행기 검증 26개를 추가한 현재 전체 테스트는 **301개 통과**이며 PowerShell 문법 검사도 통과했다. 실제 1.7B 요청 실측과 Wiki 반영은 아직 하지 않았다.

이 세션의 마지막 읽기 전용 확인에서 Ollama `/api/ps`는 HTTP 200이었고, 웹 서버 `/health`는 연결 시간 초과였다. 프로세스 열거만으로 현재 서비스 상태를 단정하지 않는다. 세 범위의 PID를 확인하기 전에는 실측하지 않는다.

## 사용 순서

### 사용자 PowerShell에서 자동 PID 확인

Codex 실행 환경에서 사용자 프로세스가 보이지 않을 때는 서버를 실행한 창을 유지하고 **별도 사용자 PowerShell**에서 프로젝트 폴더로 이동해 다음을 실행한다.

```powershell
.\.venv\Scripts\python.exe memory_launch.py --prepare-model --run --confirm-interactively
```

다른 채팅·업로드·재색인·Ollama 요청이 없음을 확인하고 `MEASURE`를 입력한다. 동일한 실행의 PowerShell 래퍼는 `./measure-memory.ps1 -PrepareModel -Run`이다. 스크립트 실행 정책이 제한된 경우 정책을 변경하지 않고 위 Python 명령을 사용한다.

- `memory_launch.py`의 기본 실행은 읽기 전용이다. `--prepare-model`이 없으면 모델을 적재하지 않고, `--run`이 없으면 실제 측정을 하지 않는다.
- 8000·11434 포트의 실제 listener PID를 읽고 프로젝트 경로·명령·프로세스 생성 시각을 검증한다. PID가 없거나 모호하거나 접근이 거부되면 중단한다. runner도 서비스 자식 중 하나로 확인해야 한다. 최종 범위·환경·모델 검증은 기존 수집기가 다시 수행한다.
- 모델 준비는 설치된 `qwen3:1.7b`만, 적재된 모델이 없을 때만 허용한다. 다른 모델을 unload하거나 다운로드하지 않는다. 준비 요청 직전 상태를 재확인하지만 외부 요청과 원자적으로 잠글 수는 없으므로 사용자 동시 작업 중단 확인이 필요하다.
- 명시적인 준비 요청은 빈 prompt로 모델을 적재하고 `keep_alive=15m`를 사용한다. 모델 적재는 RSS 측정 구간 밖이다. 실제 측정 요청은 기존 프로토콜대로 예열 1회·유휴 5초·실측 5회를 실행한다. 준비 중 실패해도 모델을 자동 종료하지 않는다.
- 실행기는 서버를 시작·종료하지 않으며, 기존 수집기의 로컬 JSON 저장 및 Wiki 자동 기록 금지를 유지한다. 실행기 단계에서 중단되면 수집기 JSON이 아직 없을 수 있으며 콘솔 오류를 보존한다.
- 새 실행기의 자동 검증은 가상 프로세스·HTTP 응답 기반이다. 사용자 PC에서 실제 5회 실측 성공을 확인한 것은 아니다.

### PID 직접 지정

1. 웹 서버를 현재 코드로 실행한다. Ollama 및 `qwen3:1.7b` 모델이 이미 실행 중인지 확인한다. 다른 사용자 작업이나 모델을 자동 종료하지 않는다.
2. 실제 웹 서버, Ollama 서비스, 해당 모델 runner의 PID를 확인한다. 프로세스 이름만으로 추측하지 않는다.
3. 다음 읽기 전용 사전 확인을 실행한다. PID 자리에는 실제 확인한 번호를 넣는다.

```powershell
python memory_benchmark.py --web-pid <웹서버PID> --ollama-pid <서비스PID> --runner-pid <모델runnerPID>
```

이 명령은 프로세스 RSS와 서버/모델 상태를 읽고 로컬 보고서를 남기지만 모델 생성 요청을 보내지 않는다. 사전 확인이 통과하고 다른 요청·업로드·재색인이 없음을 확인한 뒤에만 다음을 실행한다.

```powershell
python memory_benchmark.py --web-pid <웹서버PID> --ollama-pid <서비스PID> --runner-pid <모델runnerPID> --run --exclusive-confirmed
```

`<...>`는 설명용 자리 표시이며 그대로 실행하지 않는다. 프로젝트의 가상환경을 활성화한 터미널에서 실행한다.

## 동작과 안전 제한

- 기본은 읽기 전용 사전 확인. `--run`과 `--exclusive-confirmed`가 모두 있어야 예열 1회·유휴 5초·측정 5회를 실행한다. 회차 사이 대기는 3초다.
- 실제 프로젝트 경로의 단일 FastAPI 서버와 `serve`/`runner` 명령을 확인한다. Ollama 서비스의 모든 자식이 확인된 runner 트리에 속해야 한다. 모호한 추가 자식이나 서로 겹치는 측정 범위는 거절한다.
- 서비스는 본체만, 웹 서버와 runner는 각각 확인된 자식까지 측정한다. PID·생성 시각을 고정하고 변경·재사용을 기록하며 측정을 중단한다.
- 활성 모델은 정확히 `qwen3:1.7b` 하나여야 한다. 자동 다운로드·적재·unload는 하지 않는다. 모델 digest·실제 웹 서버 옵션·소스 지문을 요청 전후에 확인한다.
- 웹 서버의 환경에서는 허용된 설정 키만 기록한다. 전체 환경이나 전체 명령행을 보고서에 저장하지 않는다. 서버가 실행된 뒤 소스가 바뀌었다면 재시작을 요구한다.
- RSS 원자료는 바이트다. 100ms 표본과 구간 시작/끝 표본을 남기며, 불규칙 간격은 시간 가중 평균으로 처리한다. 프로세스 읽기는 원자적이지 않으므로 읽기 종료 시각도 남긴다.
- 수집 창은 요청 직전 스냅샷부터 응답 후 스냅샷까지다. 요청의 실제 시작·종료 시각을 별도로 기록한다. 경계 표본 읽기 비용이 포함되므로 API 응답시간과 동일하다고 주장하지 않는다.
- 표본 최대는 순간 최대의 보장이 아니다. 공유 페이지가 중복될 수 있어 RSS 합계를 고유 물리 메모리 사용량으로 해석하지 않는다.
- 접근 거부·프로세스 종료·PID 변경·요청 실패를 0으로 바꾸지 않는다. 이미 읽은 원자료는 남기되 오류가 있는 표본은 유효 집계에서 제외하는 것이 아니라 **해당 구간 전체를 무효**로 만든다. 자동 재시도하지 않는다.
- 기본 보고서는 사전 확인 결과이며 실측 결과가 아니다. 완료 실험은 `completed`, 중단 실험은 `blocked_or_incomplete` 상태로 구분한다. 실측 완료는 5개 회차와 전후 확인이 모두 성공해야 한다.
- 원자료·실행 정보·회차 요약은 하나의 로컬 `benchmark-results/memory-rss-*.json`에 저장한다. Wiki는 쓰지 않는다. MiB 변환 및 Wiki용 표 작성은 사람 검토 후 별도 단계다.

## 지원 한계

현재는 단일 서버·단일 미리 적재된 모델의 확인된 프로세스 트리를 지원한다. 예전 Ollama에서 runner 명령 구조가 다르거나 프로세스 환경/부모 관계를 읽지 못하면 추측하지 않고 중단한다. 별도 프로세스의 동시 요청 유무를 도구가 완전히 증명할 수 없어 사용자 확인을 요구한다. 전원 상태와 CPU 정보는 실행 담당자가 별도로 확인해야 한다.

‘프로토콜 문서의 모든 메타데이터가 자동 수집된다’는 의미는 아니다. 도구는 OS·Python·psutil·Ollama 버전, 커밋/추적 파일 변경 상태, 소스 지문, 모델 digest와 허용된 옵션을 기록한다. 프레임워크 버전·CPU·전원 상태는 후속 수집 보완 항목이다.

## 검증 결과

가상 데이터로 시간 가중 계산, 0과 누락 구분, PID 재사용, 중복·잘못된 부모 관계, 부분 읽기 실패, 요청 오류, 생성 없는 답변 거부 및 경계 표본 보존을 확인했다. 명령 도움말도 실행 확인했다. 실제 프로세스를 상대로 사전 확인/실측 전체 흐름을 통과했다고 주장하지 않는다.

첫 전체 테스트는 HTTP 테스트 내부 로컬 소켓 생성에서 대기했다. 요청한 네트워크 권한이 적용된 후 전체 테스트를 다시 실행해 `275 passed`를 확인했다. 애플리케이션이나 테스트의 네트워크 보호를 해제하는 코드 변경은 하지 않았다.

분리 수집기 구현 후 사용자 PowerShell용 자동 PID 확인 실행기를 추가했다. 다음은 사용자가 실행한 서버를 유지한 채 위 명령으로 실제 1.7B 측정을 수행하는 단계다. 실제 완료 보고서가 나오기 전에는 실측 성공이나 Wiki 반영을 주장하지 않는다.
