# 분리 메모리 수집 도구 — 2026-10-08

## 상태

사용자 PowerShell에서 첫 1.7B 실측과 절대 목표 시각 스케줄러 재측정을 각각 5회 완료했다. [1.7B 기록](MEMORY-MEASUREMENT-20261008.md)·[4B 기록](MEMORY-MEASUREMENT-4B-20261008.md)·[7B 및 세 모델 요약](MEMORY-MEASUREMENT-7B-20261008.md)에 조건·원자료 지문·결과·간격 한계를 남겼다. 세 모델 각각 5회 모두 유효하지만 특히 7B는 최대 간격 약 1.07초로 정밀 피크 비교를 보류한다. Wiki에는 반영하지 않았다.

초기 Codex 실행 환경에서는 프로세스 목록이 보이지 않고 서버 연결 확인도 실패했다. 이후 사용자 PowerShell에서 서버를 유지한 채 실행기로 PID를 검증해 초회 측정을 완료했다. 서비스 상태를 이름이나 이전 PID로 추측하지 않으며 매 실행 시 다시 확인한다.

## 사용 순서

### 사용자 PowerShell에서 자동 PID 확인

Codex 실행 환경에서 사용자 프로세스가 보이지 않을 때는 서버를 실행한 창을 유지하고 **별도 사용자 PowerShell**에서 프로젝트 폴더로 이동해 다음을 실행한다.

```powershell
.\.venv\Scripts\python.exe memory_launch.py --prepare-model --run --confirm-interactively
```

다른 채팅·업로드·재색인·Ollama 요청이 없음을 확인하고 `MEASURE`를 입력한다. 동일한 실행의 PowerShell 래퍼는 `./measure-memory.ps1 -PrepareModel -Run`이다. 스크립트 실행 정책이 제한된 경우 정책을 변경하지 않고 위 Python 명령을 사용한다.

- `memory_launch.py`의 기본 실행은 읽기 전용이다. `--prepare-model`이 없으면 모델을 적재하지 않고, `--run`이 없으면 실제 측정을 하지 않는다.
- 8000·11434 포트의 실제 listener PID를 읽고 프로젝트 경로·명령·프로세스 생성 시각을 검증한다. PID가 없거나 모호하거나 접근이 거부되면 중단한다. runner도 서비스 자식 중 하나로 확인해야 한다. 최종 범위·환경·모델 검증은 기존 수집기가 다시 수행한다.
- 모델 준비는 설치된 `qwen3:1.7b`만, 적재된 모델이 없을 때만 허용한다. 다른 모델을 unload하거나 다운로드하지 않는다. 준비 요청 직전 상태를 재확인하지만 외부 요청과 원자적으로 잠글 수는 없으므로 사용자 동시 작업 중단 확인이 필요하다.
- 명시적인 준비 요청은 빈 prompt로 모델을 적재하고 `keep_alive=15m`를 사용한다. 모델 적재는 RSS 측정 구간 밖이다. 실제 측정 요청은 기존 프로토콜대로 예열 1회·유휴 5초·실측 5회를 실행한다. 준비 중 실패해도 모델을 자동 종료하지 않는다.
- 실행기는 서버를 시작·종료하지 않으며, 기존 수집기의 로컬 JSON 저장 및 Wiki 자동 기록 금지를 유지한다. 실행기 단계에서 중단되면 수집기 JSON이 아직 없을 수 있으며 콘솔 오류를 보존한다.
- 새 실행기의 자동 검증은 가상 프로세스·HTTP 응답 기반이다. 사용자 PC에서 실제 5회 실측 성공을 확인한 것은 아니다.

### 4B·7B 선택

기본 모델은 이전과 같은 `qwen3:1.7b`다. 프로젝트 모드에 등록된 정확한 이름만 허용한다. 세 모델 각각 실제 5회 수집을 완료했으며 표본 지연 한계는 모델별 기록에 남겼다.

| 선택 | 정확한 모델 이름 | 상태 |
|---|---|---|
| 1.7B | `qwen3:1.7b` | 첫 측정·재측정 완료 |
| 4B | `qwen3:4b-instruct` | 실제 5회 측정 완료, 표본 지연 경고 포함 |
| 7B | `qwen2.5:7b-instruct` | 실제 5회 측정 완료, 큰 표본 지연 경고 포함 |

서버 창은 유지한다. 다른 작업을 멈추고 `ollama ps`로 활성 모델을 확인한다. 1.7B 작업이 끝났고 해당 모델만 적재되어 있다면 **사용자가 직접** `ollama stop qwen3:1.7b`를 실행하거나 만료될 때까지 기다릴 수 있다. 실행기는 모델을 자동 종료·교체·다운로드하지 않는다. 설치되지 않은 모델이나 다른 활성 모델이 있으면 중단한다.

```powershell
.\.venv\Scripts\python.exe memory_launch.py --model qwen3:4b-instruct --prepare-model --run --confirm-interactively
```

4B 결과 검토 후 4B 작업을 마치고 사용자가 해당 모델을 종료하거나 만료를 기다린 뒤 7B를 별도로 측정한다.

```powershell
.\.venv\Scripts\python.exe memory_launch.py --model qwen2.5:7b-instruct --prepare-model --run --confirm-interactively
```

PowerShell 래퍼의 모델 옵션은 `-Model qwen3:4b-instruct` 또는 `-Model qwen2.5:7b-instruct`다. PID 직접 지정 수집기에도 `--model`을 지정해야 하며, 실행기는 선택값을 자동 전달한다. 모델 하나마다 독립 보고서를 남긴다. 서버를 재시작하거나 기본 채팅 모델을 바꾸지는 않는다.

고정 기준 JSON은 수정하지 않고 선택 모델의 실행용 프로토콜을 복사한다. 샘플 목표 100ms·예열 1회·측정 5회·질문·num_ctx 2048·num_predict 256·temperature 0.3·think false는 유지한다. 원래 1.7B의 `protocol_sha256`은 기준 파일 바이트 지문을 유지하고, 4B/7B는 실행용 프로토콜의 정렬된 compact JSON 지문이다. `protocol_hash_format`이 둘을 구분하며 `base_protocol_sha256`과 `effective_protocol_sha256`도 기록한다. 모델을 바꿨는데 동일 프로토콜 지문이라고 주장하지 않는다.

기존 서버 로직은 1.7B의 질문에 `/no_think`를 덧붙이고 instruct 모델에는 덧붙이지 않는다. 이 차이를 실행용 프로토콜 note에 기록한다. 7B는 Qwen2.5이고 1.7B·4B는 Qwen3 계열이므로 단순 크기 효과나 같은 모델의 확장 실험이라고 해석하지 않는다. 출력 길이·CPU 부하·적재 상태도 별도 확인해야 한다.

### PID 직접 지정

1. 웹 서버를 현재 코드로 실행한다. Ollama 및 `qwen3:1.7b` 모델이 이미 실행 중인지 확인한다. 다른 사용자 작업이나 모델을 자동 종료하지 않는다.
2. 실제 웹 서버, Ollama 서비스, 해당 모델 runner의 PID를 확인한다. 프로세스 이름만으로 추측하지 않는다.
3. 다음 읽기 전용 사전 확인을 실행한다. PID 자리에는 실제 확인한 번호를 넣는다.

```powershell
python memory_benchmark.py --web-pid <웹서버PID> --ollama-pid <서비스PID> --runner-pid <모델runnerPID>
```

이 명령은 프로세스 RSS와 서버/모델 상태를 읽고 로컬 보고서를 남기지만 모델 생성 요청을 보내지 않는다. 사전 확인이 통과하고 다른 요청·업로드·재색인이 없음을 확인한 뒤에만 다음을 실행한다.

```powershell
python memory_benchmark.py --web-pid <웹서버PID> --ollama-pid <서비스PID> --runner-pid <모델runnerPID> --run --exclusive-confirmed
```

`<...>`는 설명용 자리 표시이며 그대로 실행하지 않는다. 프로젝트의 가상환경을 활성화한 터미널에서 실행한다.

## 동작과 안전 제한

- 기본은 읽기 전용 사전 확인. `--run`과 `--exclusive-confirmed`가 모두 있어야 예열 1회·유휴 5초·측정 5회를 실행한다. 회차 사이 대기는 3초다.
- 실제 프로젝트 경로의 단일 FastAPI 서버와 Ollama `serve` 명령을 확인한다. runner는 동일 Ollama 실행 파일의 `runner` 명령 또는 확인된 Windows llama-server 형식을 인정한다. 서비스 자식은 확인된 runner 트리와 아래에서 검증한 직속 시스템 콘솔 호스트만 허용한다. 모호한 추가 자식이나 서로 겹치는 측정 범위는 거절한다.
- 사용자 프로세스 조회에서 서비스 직속 `conhost.exe`와 runner 직속 `conhost.exe`가 각각 확인됐다. 서비스 직속 호스트는 Windows 환경에서 `%SystemRoot%/System32/conhost.exe` 실제 실행 경로와 부모 PID를 확인해야만 제외한다. PID·생성 시각을 고정하고 모든 표본에 `excluded_service_console_hosts` 목록을 남긴다. 제외 목록 변경·PID 재사용·접근 거부·웹/runner 범위 중복은 중단 사유다. 이름만 같은 임의 프로세스는 허용하지 않는다.
- 서비스 RSS는 원래 기준대로 본체만이다. runner RSS는 자식 콘솔 호스트를 포함한 트리 합계다. 따라서 세 범위 RSS를 더해 전체 Ollama 설치 구성의 RSS라고 주장하지 않는다. 서비스 콘솔 호스트 RSS 자체는 이번 프로토콜에서 측정하지 않는다.
- 사용자가 제공한 Ollama 0.40.0 정보는 `ollama.exe serve`의 자식인 `lib/ollama/llama-server.exe`였다. 해당 설치 경로의 실제 실행 파일·명령행 실행 파일 경로, 절대 경로 `models/blobs/sha256-<64자리>` 모델, 유효 포트·127.0.0.1 host·offline/no-webui 옵션을 함께 검증한다. 임의 llama-server나 이름만 같은 프로세스는 인정하지 않는다. 모델 blob 해시와 `/api/ps` 모델 manifest digest가 같다고 주장하지 않는다.
- 서비스는 본체만, 웹 서버와 runner는 각각 확인된 자식까지 측정한다. PID·생성 시각을 고정하고 변경·재사용을 기록하며 측정을 중단한다.
- 활성 모델은 정확히 `qwen3:1.7b` 하나여야 한다. 자동 다운로드·적재·unload는 하지 않는다. 모델 digest·실제 웹 서버 옵션·소스 지문을 요청 전후에 확인한다.
- 웹 서버의 환경에서는 허용된 설정 키만 기록한다. 전체 환경이나 전체 명령행을 보고서에 저장하지 않는다. 서버가 실행된 뒤 소스가 바뀌었다면 재시작을 요구한다.
- RSS 원자료는 바이트다. 100ms 표본과 구간 시작/끝 표본을 남기며, 불규칙 간격은 시간 가중 평균으로 처리한다. 프로세스 읽기는 원자적이지 않으므로 읽기 종료 시각도 남긴다.
- 현재 목표 간격은 100ms이며 보장 간격이 아니다. `absolute-deadline-v2`는 최초 표본 시각 기준 목표 시각을 유지하고 이미 지난 목표는 건너뛴다. 표본의 `sample_role`은 start/periodic/end이며, 주기 표본의 `schedule`은 목표 시각·실제 시작 지연·직전 건너뛴 횟수다. 구간별 `sampling_schedule.skipped_ticks`는 목표 누락 수이고 종료 경계 표본을 건너뛴 수가 아니다. `read_end`는 읽기 비용 확인에 사용한다. 종료 대기 전 건너뛴 목표는 합계에 포함될 수 있다.
- 수집 창은 요청 직전 스냅샷부터 응답 후 스냅샷까지다. 요청의 실제 시작·종료 시각을 별도로 기록한다. 경계 표본 읽기 비용이 포함되므로 API 응답시간과 동일하다고 주장하지 않는다.
- 표본 최대는 순간 최대의 보장이 아니다. 공유 페이지가 중복될 수 있어 RSS 합계를 고유 물리 메모리 사용량으로 해석하지 않는다.
- 접근 거부·프로세스 종료·PID 변경·요청 실패를 0으로 바꾸지 않는다. 이미 읽은 원자료는 남기되 오류가 있는 표본은 유효 집계에서 제외하는 것이 아니라 **해당 구간 전체를 무효**로 만든다. 자동 재시도하지 않는다.
- 기본 보고서는 사전 확인 결과이며 실측 결과가 아니다. 완료 실험은 `completed`, 중단 실험은 `blocked_or_incomplete` 상태로 구분한다. 실측 완료는 5개 회차와 전후 확인이 모두 성공해야 한다.
- 원자료·실행 정보·회차 요약은 하나의 로컬 `benchmark-results/memory-rss-*.json`에 저장한다. Wiki는 쓰지 않는다. MiB 변환 및 Wiki용 표 작성은 사람 검토 후 별도 단계다.

## 지원 한계

현재는 단일 서버·단일 미리 적재된 모델의 확인된 프로세스 트리를 지원한다. 지원한 두 실행 형태와 다른 runner 구조이거나 프로세스 환경/부모 관계를 읽지 못하면 추측하지 않고 중단한다. 별도 프로세스의 동시 요청 유무를 도구가 완전히 증명할 수 없어 사용자 확인을 요구한다. 전원 상태와 CPU 정보는 실행 담당자가 별도로 확인해야 한다.

‘프로토콜 문서의 모든 메타데이터가 자동 수집된다’는 의미는 아니다. 도구는 OS·Python·psutil·Ollama 버전, 커밋/추적 파일 변경 상태, 소스 지문, 모델 digest와 허용된 옵션을 기록한다. 프레임워크 버전·CPU·전원 상태는 후속 수집 보완 항목이다.

## 검증 결과

스냅샷 단계와 실제 대기의 경과/스레드 CPU 시간을 선택적으로 기록하는 `--profile-timings`를 지원한다. 기본은 OFF이고 기존 수집 규칙·오류 처리·검사 빈도는 유지한다. [계측 실행과 해석](MEMORY-PROFILING.md) 및 [실제 OFF/ON 분석](MEMORY-PROFILING-RESULT-20261008.md)을 참고한다. ON 스냅샷 경과의 98.85%가 범위 검사지만, 순수 계측 영향이나 특정 하위 호출 원인은 확정하지 않았다.

가상 데이터로 시간 가중 계산, 0과 누락 구분, PID 재사용, 중복·잘못된 부모 관계, 부분 읽기 실패, 요청 오류, 생성 없는 답변 거부 및 경계 표본 보존을 확인했다. 추가로 절대 목표 시각 유지·긴 읽기 후 건너뛰기·늦은 wakeup 기록·응답 완료 후 주기 읽기 방지·잘못된 간격 거부를 검증한다. 이전·새 스케줄러로 각각 실제 실험을 완료했고, 평균 표본 간격은 161.22ms에서 101.69ms로 관찰됐다. 신규 실험의 목표 누락 4회도 보존한다.

첫 전체 테스트는 HTTP 테스트 내부 로컬 소켓 생성에서 대기했다. 요청한 네트워크 권한이 적용된 후 전체 테스트를 다시 실행해 `275 passed`를 확인했다. 애플리케이션이나 테스트의 네트워크 보호를 해제하는 코드 변경은 하지 않았다.

현재 전체 자동 테스트는 388개 통과다. 모델 선택 검증 16개 및 선택적 계측 검증 8개, 새 부모 표 검증 25개를 포함한다. [Windows 중복 조회 개선](MEMORY-PARENT-SNAPSHOT.md)은 매 검사 한 번의 새 부모 표를 공유하며 기존 보호와 검사 빈도를 유지한다. [개선 후 7B OFF 결과](MEMORY-PARENT-SNAPSHOT-RESULT-20261008.md)는 평균 간격 122.63ms·누락 목표 110회지만 5회 모두 지연 경고가 남는다. 두 1.7B 및 4B·7B 실험의 원자료 평균을 재계산해 일치함을 확인했다. 기존 4B는 목표 누락 34회, 최초 7B는 222회여서 완전한 100ms 보장이 아니다. 수집 성공과 정밀 피크 검증은 구분하며 모든 환경에서의 재현성을 확인한 것은 아니다.
