## OFF/ON 관찰값

요청 5회 기준이며 표본 수와 읽기 통계는 시작·주기·끝 표본을 포함한다. 평균 실제 간격은 연속 표본 시간차 합계/개수이며 요청 사이 유휴는 제외한다. p95는 nearest-rank다.

ON의 관찰 간격은 더 나빴다. 타이머·기록 조립 등 계측 영향은 가능한 요인이지만 이를 순수 계측 비용으로 확정하지 않는다. 생성 토큰 수는 OFF 62/59/56/58/69, ON 52/76/55/55/68로 다르고 실행 순서·CPU 부하 등도 무작위 반복 실험으로 통제하지 않았다. 따라서 평균 차이를 빼서 정확한 타이머 비용으로 쓰거나 모델 성능 저하라고 주장하지 않는다. 기본 계측 OFF는 유지한다.

## ON 단계별 관찰값

단계별로 호출 1개의 통계다. membership은 표본당 1개, 다른 단계는 구성원당 1개라 모집단 크기가 다르다.

| identity_before 생성 시각 | 796 | 0.00794 | 0.00310 | 1.43 | 0.00 |

| identity_after PID 재확인 | 796 | 0.25 | 0.04930 | 114.22 | 0.00 |

표본별 경과 합계는 51.73052초다. membership은 51.13512초로 **98.85%**, RSS 읽기는 0.31817초로 **0.62%**다. 남은 시간은 다른 단계와 타이머·자료 조립 등이다. 이 비율은 수집기 스레드의 경과 시간 분해이지 CPU 점유율이나 전체 API 응답시간의 비율이 아니다.

ON에서 가장 오래 걸린 스냅샷은 2,443.77ms이며 그 표본의 membership은 2,349.81ms, membership CPU는 78.125ms였다. membership 자체 최대 2,384.08ms는 다른 표본이므로 서로 더하지 않는다. 넓은 범위 검사가 긴 경과 시간의 주요 관측 단계라는 근거이며 RSS 읽기 한 번의 비용이 항상 작다는 보장은 아니다.

CPU 기록은 0/15.625/31.25/46.875/62.5/78.125ms 단위 값으로 관찰됐다. 짧은 함수의 CPU 0은 무비용이나 계측 실패를 뜻하지 않는다. wall/CPU는 별도 시계이며 정밀도 차이를 고려해야 한다. 대상은 수집 스레드이고 Ollama·HTTP 작업 스레드 CPU 사용률이 아니다.

## 실제 대기 호출

ON에서 기록한 대기 호출은 189개다. 이 실행의 기록은 모두 응답 완료로 종료된 호출이 아니며, 평균 경과 77.02ms·평균 CPU 0.66ms다. 요청한 대기보다 추가된 시간은 평균 22.03ms·p95 80.59ms·최대 414.32ms다. 의도한 timeout 전체를 불필요한 지연으로 해석하지 않는다.

스냅샷 내부 경과와 별도로 대기 지연도 존재한다. 그러나 membership의 경과/CPU 차이만으로 OS 경쟁·네이티브 조회 대기·GIL 등 특정 원인을 확정할 수 없다. 이번 단계 계측은 membership 내부의 세 자식 조회·콘솔 호스트 검증을 하나의 묶음으로 기록했다.

## 판단과 다음 범위

이번 ON 실행에서 확인된 주요 병목 위치는 **membership 범위 검사**다. 다음 개선 대상은 이 안의 반복 부모/자식 조회다. 중복 조회를 안전하게 통합할 수 있는지 검토하되 매 표본의 PID/생성 시각·구성원·제외 호스트·중복 검사와 오류 중단을 유지해야 한다. 어떤 하위 호출이 얼마나 차지했는지까지 확정한 것은 아니다.
