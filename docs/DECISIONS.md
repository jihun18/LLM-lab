## D-001 FastAPI를 주력 백엔드로 사용

- 상태: 채택
- 날짜: 2026-08-14

대안:

- Flask
- Streamlit

이유:

- Pydantic 입력 검증

- 스트리밍 응답 지원

Flask는 최소 구현 학습, Streamlit은 빠른 실험 UI로 유지한다.

## D-002 기본 모델은 qwen3:1.7b

- 상태: 채택
- 개발용 보조 모델: qwen3:0.6b

0.6B는 약 2배 이상 빠르지만 사실 오류와 지시 반복이 더 자주 관찰됐다. 16GB
재평가에서도 1.7B가 4B·7B보다 빨랐다. 1.7B도 완전히 정확하지 않으므로 RAG와
검증 하니스를 전제로 사용한다. 4B는 균형 모드, 양자화 7B는 정밀 모드 후보로
남기며 사용자가 필요에 따라 선택한다.

## D-003 첫 검색 엔진은 BM25

- 상태: 채택

이유:

- 별도 임베딩 모델 불필요
- 벡터DB 불필요
- RAM 8GB 환경에 적합
- 점수와 검색 근거 설명이 쉬움

한계:

- 동의어와 의미 검색에 약함
- 한국어 조사가 붙은 같은 단어가 다르게 처리될 수 있음

다음 버전에서 경량 임베딩과 비교하되 BM25를 기준선으로 유지한다.

한국어 조사는 원형 토큰을 함께 색인해 `모델`, `모델을`, `모델로` 같은 표현의
검색 누락을 줄인다.

## D-004 코드 블록은 Wiki 검색에서 제외

사용 가이드의 예시 질문이 실제 지식 문단보다 높은 점수를 얻는 문제가 발생했다. Markdown 코드 블록을 색인에서 제외해 예시 명령과 질문이 검색 결과를 오염시키지 않도록 했다.

## D-005 검색 상대 점수 필터 사용

검색 1위와 점수 차이가 큰 관계없는 문서가 출처에 나타났다. 1위 점수의 30% 미만 후보를 제거한다. 절대 점수 대신 상대 점수를 사용해 질문별 BM25 범위 차이를 완화한다.

## D-006 확정 가능한 표 수치는 LLM을 우회

모델이 평균 속도 질문에서 평균 시간 열을 선택했다. 표 헤더와 질문 단위를 코드로 대응하고 확정 가능한 답은 LLM을 호출하지 않는다.

효과:

- 열 혼동 방지
- 숫자 환각 감소
- 즉시 응답
- 검증 근거 설명 가능

## D-007 검증 범위를 UI에 구체적으로 표시

출처가 있다는 이유만으로 일반 문장에 `검증 통과`를 표시하면 과도한 신뢰를 유발한다.

상태를 다음처럼 분리한다.

- 표 수치 검증 통과
- 금액·날짜·단위 검증 통과
- 검증 실패
- 출처 연결됨·사람 의미 검토 필요

## D-008 업로드는 원문 바이트 API 사용

FastAPI multipart 의존성을 늘리지 않기 위해 파일 바이트를 요청 본문으로 보내고 URL 인코딩 파일명을 `X-Filename` 헤더로 전달한다. 브라우저 기반 단일 파일 업로드라는 현재 범위에는 충분하다.

## D-009 업로드 원본 대신 변환 Markdown 저장

원본 PDF를 보존하지 않고 추출 텍스트와 원본 이름·해시만 Wiki에 기록한다. 저장공간과 중복을 줄이고 RAG 입력 형식을 통일하기 위한 선택이다.

향후 원본 보관이 필요해지면 별도 암호화 저장소와 삭제 정책을 먼저 설계한다.

## D-010 모델 출처는 검색 결과와 일치할 때만 표시

- 상태: 채택
- 날짜: 2026-09-23

모델이 출처 예시 문자열이나 검색되지 않은 문서를 그대로 출력할 수 있다. 답변의
`[출처: 파일명#제목]`을 실제 검색 결과와 대조하고, 일치하지 않거나 출처가 없으면
답변을 차단한다. 이는 의미 전체의 사실성 검증을 대체하지 않는다.
